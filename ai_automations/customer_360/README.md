# Customer 360 — обзор заказчика (DEMO)

## Что это
Объяснимый обзор истории перевозок клиента; правила, а не обученный AI/LLM.
## Какую проблему решает
Менеджер вручную ищет историю и дату последней перевозки. Демонстрация собирает сведения в одном ответе.
## Как работает
1. Читает синтетический `example_input.json`. 2. Сопоставляет `partner_id`. 3. Считает заказы, неоплаченные заказы и дни после последнего заказа. 4. Отмечает клиента при 90+ днях без заказа.
## Какие данные использует
В будущем: `res.partner` (id, name), `ufs.base.order` (partner_id, order_date, is_paid); сейчас исключительно файл примера. Это не данные ERP.
## Что делает AI
AI-модель не используется: детерминированная сегментация на основе даты среза.
## Результат
JSON со статусом `DEMO`, причиной рекомендации и числом клиентов для ручной проверки.
## Как запустить
Из корня репозитория: `python3 ai_automations/customer_360/run.py`. Требуется Python 3.9+, внешних зависимостей нет. Можно передать `--input /path/to/synthetic.json`; `--mode live` честно отклоняется. Для проверки: `python3 -m unittest discover -s ai_automations/tests`.
## Пример
Вход: у «Демо Север» последний заказ 2026-05-02; срез 2026-09-28. Обработка: 149 дней >= 90. Выход: `attention=review_reactivation`, `reason=Последний заказ 149 дней назад` (смотрите полный `example_output.json`).
## Плюсы
Прозрачное правило, не отправляет сообщения, запускается без Odoo.
## Минусы
Порог произвольный, не учитывает сезонность или переговоры.
## Риски
Неполная история даст ложный сигнал. Неоплата в примере — булевый флаг, а не финансовая сверка.
## Human-in-the-loop
Менеджер проверяет заказчика и контактные предпочтения перед любым звонком/письмом.
## Техническая архитектура
Локальный `run.py` → `../engine.py` → JSON stdout; read-only, без сети.
## Ограничения
DEMO MODE работает; LIVE MODE не реализован без согласования API, прав, качества данных и согласий. Нет CRM-скоринга/LLM и измеренной экономии.
