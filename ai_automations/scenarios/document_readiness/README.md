# Document Readiness — готовность пакета (DEMO)

## Что это
Проверка наличия успешного статуса AI-проверки по каждому обязательному типу документа.
## Какую проблему решает
Логисту приходится сверять список документов и замечаний вручную.
## Как работает
1. Получает утверждённый список типов. 2. Группирует статусы `ufs.ai.document.check`-подобных записей по заказу. 3. Помечает отсутствующие и не завершённые типы. 4. Даже успешный статус означает только готовность к ручному просмотру.
## Какие данные использует
Синтетические `checks` в `example_input.json`; потенциальные источники: `ufs.ai.document.check` (state, document_type, base_order_id) и `ufs.transport.document`. Типы и обязательность в demo — условные, не правило Odoo.
## Что делает AI
Ничего: это детерминированная сверка. Существующий `repka_ai_document_check` использует mock, а не реальное OCR.
## Результат
JSON с `missing`, `needs_review`, статусом и причиной.
## Как запустить
`python3 ai_automations/scenarios/document_readiness/run.py` (Python 3.9+, без дополнительных библиотек), свой синтетический файл — `--input /path/to/file.json`; `--mode live` отклоняется. Тесты: `python3 -m unittest discover -s ai_automations/.internal/tests`.
## Пример
Вход: заказ 101 с CMR в статусе `blocked` и без акта; выход: `needs_review=["cmr"]`, `missing=["act"]`, `status=review` (полный `example_output.json`).
## Плюсы
Явно показывает пробелы, не изменяет заказы.
## Минусы
Не читает и не распознаёт сканы; статусы могут устареть.
## Риски
`completed` не доказывает юридическую корректность; ошибочная полнота списка тоже опасна.
## Human-in-the-loop
Логист проверяет оригинал каждого документа; закрытие заказа через этот CLI невозможно.
## Техническая архитектура
Локальный `run.py` → `../../.internal/engine.py` → JSON stdout; никаких HTTP/Odoo-операций.
## Ограничения
DEMO MODE работает на синтетических статусах. LIVE MODE требует проверки связи заказа с документами, ACL и политики обязательности.
