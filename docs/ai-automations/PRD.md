# PRD: Repka AI Automations

## Проблема и пользователи
Логисты, менеджеры и руководство вручную собирают историю заказов, проверяют документы и оценивают финансовые риски. В репозитории есть модели и экранные формы, но нет подтверждённой репрезентативной истории для обучения моделей и подтверждённого доступа отдельного аналитического сервиса к Odoo.

## Цель и ценность
Создать проверяемый, безопасный демонстрационный каталог аналитических автоматизаций на синтетических данных, показывающий решения и объяснения без изменений бизнес-данных. Ценность live-версии должна быть оценена по реальным данным и времени сотрудников, а не по вымышленным процентам.

## Границы MVP
Четыре независимых сценария: профиль клиента, контроль экономики перевозок, готовность пакета документов и сводка руководителю. Каждый запускается CLI без сетевых запросов, имеет тесты и отдельные входные данные. Каталог охватывает также нереализованные идеи. Не входят live-доступ, запись в Odoo, обучение ML, OCR, массовая отправка сообщений, автоматическое принятие решений. Уже существующий `repka_ai_document_check` остаётся без изменений.

## Требования
- Явно показывать статус DEMO и метод (детерминированные правила, не LLM).
- Только синтетические данные; отдельные сценарии и общий launcher; стабильный JSON-вывод.
- Проверка схемы входа и ошибок; неизменность входных файлов; повторы с одинаковым результатом.
- Доступность на Python 3.9+ без обязательных внешних зависимостей; отсутствие записи в ERP и секретов.
- Флаги live не должны незаметно переходить в demo.

## Данные
Подтверждённые поля: `ufs.base.order` (partner_id, company_id, order_date, freight_amount, currency_id, has_act, is_paid), `ufs.forwarder.order` (base_order_id, suborder_amount_sum, full_profitability, ufs_attached_document_ids), `ufs.ai.document.check` (state, document_type, check_line_ids), `res.partner`. Поля сами по себе не означают наличие заполненных транзакций или сопоставимых денежных величин. Демонстрационные JSON-данные полностью вымышлены.

## Метрики и приёмка
Метрики будущего пилота: точность предупреждений по ручной разметке, доля полезных предложений, доля неподтверждённых данных, время подготовки отчёта до/после и количество ошибок. Приёмка MVP: каждый сценарий дважды запускается без ошибок, выдаёт согласованный объяснимый ответ, ошибочные входные данные отклоняются, PPTX открывается и не обещает несуществующего AI.

## Риски и следующий этап
Риски: неверные валюты, неполные документы, отсутствие себестоимости, утечка персональных данных, переоценка возможностей эвристик. Для live-пилота нужны утверждённые источники, ограниченная сервисная учётная запись, согласие на обработку данных, проверка ACL/record rules, аудит и набор размеченных кейсов.
