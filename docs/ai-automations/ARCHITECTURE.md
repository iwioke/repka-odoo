# Architecture: Repka AI Automations

## Подтверждённые факты
Odoo 18 CE и PostgreSQL 16 развёрнуты через Docker Compose. Мета-модуль `repka_suite` включает CRM, sales, purchase, stock, а также логистические модели. `repka_ai_document_check` посылает HTTP-запросы отдельному внутреннему сервису, который сейчас детерминированный mock. Заказы и документы присутствуют в схеме; качество и объём реальных данных не проверены. В репозитории не обнаружено отдельного API-контроллера для новых сценариев. Odoo предоставляет штатный интерфейс, но его доступ и ACL для нового внешнего сервиса не проверены.

## Принятые решения для безопасного MVP
`ai_automations/` — отдельные CLI-модули и общая библиотека только Python stdlib. Вход — валидируемые локальные JSON-файлы с синтетическими данными; выход — человекочитаемый JSON в stdout; запуск без сети и без модификации Odoo. Каждый модуль имеет свой исполняемый entrypoint, пример и тест. `--mode live` возвращает понятную ошибку до настройки интеграции. Сценарии рассчитывают правила и описательные метрики, а не обученную модель; термин «AI» здесь обозначает пространство решений, а не факт применения LLM.

## Предложение для live-пилота (НЕ реализовано)
Odoo REST/RPC или отдельный ограниченный серверный метод → минимизированный DTO → внутренний сервис аналитики → рекомендация с причиной → проверка менеджером. Только read-only по нужным моделям с record rules и компанией; секрет в vault, TLS, короткие таймауты, ограничение объёма, audit trail, удаление временных данных по политике. Никакого прямого SQL-доступа, sudo на выгрузку или отправки контактов внешним моделям без согласования. Повторы по идентификатору задания; сбой интеграции не меняет заказ. Межвалютные суммы конвертировать на дату операции либо выводить отдельно.

## Открытые вопросы (блокируют live, но не demo)
- Что: какие отделы и типы заказов включить, есть ли достоверные прошлые данные о закупочных затратах, стадиях и документах?
- Как: через какой одобренный Odoo API читать данные, под какой ролью и record rules, как измерять качество и исправлять ошибочные рекомендации?
- Зачем: какие решения сотрудников требуют объяснений, кто подтверждает действия, какие критерии полезности?
- Интеграции: допустима ли внутренняя OCR/LLM-служба, что делать с уже существующим mock, есть ли шина событий?
- Инфраструктура: хост, нагрузка, очередь, мониторинг, бюджет, доступность, резервирование?
- Безопасность: где хранятся токены, где географически обрабатываются данные, согласия, срок хранения, журнал доступа?
- Роли: какие менеджеры видят стоимость/прибыль, кто может назначать задачи или отправлять письма?
- Эксплуатация: ответственный за сбои и ложные срабатывания, расписание, SLA и политика остановки автоматизации?

До ответа на эти вопросы никакие изменения бизнес-логики Odoo не вносятся.
