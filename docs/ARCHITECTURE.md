# Архитектура LM GROUP: текущее состояние и целевой контур

**Статус:** результат Этапа 0; не является разрешением на развёртывание или изменение инфраструктуры.
**Дата аудита:** 2026-10-13

## 1. Границы и принципы

Цель — дополнить существующий `repka-odoo` безопасным корпоративным AI-приложением LM GROUP, не заменяя работающие Odoo-компоненты без обоснования.

Обязательные границы:

- никаких VPN, туннелей или обязательных входящих соединений к офисным узлам;
- пользователи обращаются к утверждённому домену по HTTPS;
- Windows Server остаётся критичным файловым сервером и не получает публичный frontend/backend на первом этапе;
- Mac mini и файловый connector работают только через исходящие защищённые соединения;
- production, DNS, firewall, Odoo.sh и сетевые порты не меняются в рамках аудита;
- каждое действие с документами и Odoo проходит серверную авторизацию и аудит.

## 2. Текущая архитектура: подтверждённые факты

### 2.1 Odoo и инфраструктура разработки

| Компонент | Подтверждённое состояние | Вывод |
|---|---|---|
| Odoo | Community Edition `18.0-20251222`, закреплённый digest образа | Версия текущего репозитория установлена; это **не** доказательство версии Odoo.sh. |
| PostgreSQL | `16.14-bookworm`, закреплённый digest | Работает в закрытой Docker-сети `backend`. |
| Reverse proxy | Caddy в production Compose | Публикует только 80/443 и проксирует Odoo; TLS и базовые security headers уже предусмотрены. |
| Development | Odoo публикуется только на `127.0.0.1:8069` | Хорошая локальная граница; публичным приложением не является. |
| Секреты | Файлы в `secrets/`, создаваемые `scripts/init.sh` с режимами 0700/0600 | Подход пригоден для локального контура; секреты не попадают в Git. |
| Backup | `scripts/backup.sh` делает PostgreSQL dump, проверяет `pg_restore --list`, архивирует filestore и SHA-256 | Нет подтверждения расписания, off-site копии и восстановления. |

Источник: `Dockerfile`, `compose.yaml`, `compose.dev.yaml`, `compose.prod.yaml`, `Caddyfile`, `scripts/init.sh`, `scripts/backup.sh`.

### 2.2 Модули и уже существующая AI-функциональность

В `addons/` находится набор пользовательских Odoo 18 модулей для логистики, экспедирования, транспорта, счетов и отчётности. `repka_suite` является агрегирующим модулем, который включает базовые, логистические, fleet-, invoicing- и AI-модули.

Уже реализовано:

- `repka_ai_document_check` — очередь проверок документов со статусами, cron-обработкой, HTTP-вызовом endpoint, результатами и ручным override для назначенной группы;
- `services/ai_document_check_mock` — детерминированный development mock, который определяет результат по имени файла, а не анализирует документ;
- `ai_automations/` — четыре детерминированных сценария на синтетических данных (`customer_360`, `margin_watch`, `document_readiness`, `executive_brief`), для которых LIVE mode намеренно отклоняется;
- `ai_automations/app/` — локальное loopback-only веб-демо без аутентификации, запускающее только зарегистрированные demo-сценарии с ограничением времени, размера входа/выхода и без shell.

Это не RAG, не Ollama и не production AI-сервис. Существующие компоненты следует сохранить как изолированные демо и как примеры безопасных ограничений, а не публиковать как корпоративный assistant.

### 2.3 UI/UX reference: iwiqoVPN

Репозиторий `iwiqoVPN` изучен исключительно как референс интерфейса. Допустимо адаптировать:

- структуру design tokens: фон, поверхности, границы, три уровня текста, status colors и accent;
- компактные карточки и прогрессивное раскрытие деталей;
- понятное status-driven состояние с короткими анимациями;
- явный статус недоступного локального AI worker.

Не допускается перенос `VPNManager`, WireGuard, `wg-quick`, sudoers-правил, Telegram-конфигурации, VPN-моделей, entitlements или иной сетевой механики.

## 3. Целевая архитектура-кандидат

Это рекомендуемая схема для проверки после ответов администратора. Она не предполагает, что VPS, DNS, IdP или доступ к Odoo.sh уже есть.

```text
Сотрудник в браузере macOS
          |
          | HTTPS / утверждённый домен
          v
+-------------------------------------------+
| Публичный контур (отдельный VPS, если     |
| подтверждён и согласован)                 |
|                                           |
| Caddy / TLS                               |
| Web PWA + Backend API                     |
| Auth / RBAC / Audit / Rate limiting       |
| PostgreSQL + разрешённый индекс            |
| Broker / очередь типизированных задач     |
+------------------+------------------------+
                   ^
                   | исходящие TLS/mTLS, heartbeat,
                   | short-lived credentials
       +-----------+------------+
       |                        |
       v                        v
+---------------+        +-----------------------+
| Mac mini M4   |        | Office file connector |
| Ollama        |        | минимальные права     |
| allowlisted   |        | selected folders only |
| AI worker     |        +-----------+-----------+
+---------------+                    |
                                     | локально, с source-side ACL
                                     v
                              Windows file server
                              (не публикуется в internet)
```

### 3.1 Публичный контур

После отдельного согласования публичный контур предоставляет:

- PWA и backend API;
- индивидуальную аутентификацию, сессии, MFA для администраторов, RBAC и отзыв сессий;
- аудит входов, изменений прав, индексации, запросов к знаниям, генерации черновиков и действий Odoo agent;
- очередь идемпотентных фоновых задач;
- хранилище метаданных, задач и разрешённого индекса документов — только при утверждении политики хранения и обработки данных.

Внешне необходимы только 443/TCP и, если выбран ACME HTTP challenge, 80/TCP. PostgreSQL, Redis/очередь, Ollama, Odoo internal API и административные endpoints не публикуются.

### 3.2 RAG и документы

Пайплайн должен разделять следующие шаги:

1. knowledge administrator утверждает источник и назначает ACL;
2. connector или загрузка проверяет MIME, размер, расширение, архивы и вредоносные вложения;
3. ingest формирует документ, chunks, метаданные ACL и provenance;
4. retrieval фильтрует документы и chunks по полномочиям **до** передачи контекста модели;
5. модель получает только допустимый контекст и системные инструкции, не изменяемые содержимым документа;
6. UI возвращает ответ с цитатами на документ и фрагмент либо сообщает о недостаточности источников.

Документное содержимое рассматривается как недоверенные данные. Оно не может менять system prompt, разрешать инструменты или обходить ACL.

### 3.3 Mac mini worker

Mac mini не принимает входящие интернет-соединения. Worker самостоятельно устанавливает исходящее TLS-соединение к broker/backend, проходит device authentication (предпочтительно mTLS) и принимает только подписанные типизированные задания из allowlist: например, `chat_completion` и `embedding`. Он не принимает shell-команды, URL, произвольные модели или файловые пути от пользователей.

Компонент обязан поддерживать heartbeat, reconnect, ограниченную очередь, дедупликацию по idempotency key, лимиты CPU/RAM/времени и понятный статус `local_ai_unavailable`.

### 3.4 Windows Server connector

Первый подключаемый набор — только 2–3 согласованные тестовые папки. Connector использует отдельную учётную запись с минимальными read-only правами и применяет source-side allowlist/ACL. На public backend не передаётся список всех share, не открываются SMB/RDP/SSH, не требуется входящее соединение к серверу.

Перед выдачей найденного fragment backend повторно проверяет право пользователя; metadata, embeddings, цитаты, кэш и логи не должны быть каналом обхода ACL.

### 3.5 Odoo Development Agent

Odoo agent изолирован от production:

- начинает в read-only режиме;
- использует feature branch, disposable workspace и обезличенную/тестовую БД;
- имеет ограниченные CPU, RAM, time, filesystem и outbound allowlist;
- готовит план, diff, проверки и PR;
- никогда самостоятельно не merge/deploy, не меняет схему, финансы, права или production data.

## 4. Ключевые интерфейсы и trust boundaries

| Граница | Допустимый канал | Запреты и проверки |
|---|---|---|
| Browser → public app | HTTPS | Secure cookies/tokens, CSRF/XSS защита, rate limit, server-side RBAC. |
| Public app → data stores | Private network | Не публиковать БД/индекс; отдельные accounts и least privilege. |
| Public app → Mac mini | Только ответ на outbound worker connection | mTLS или ротация коротких credentials; typed jobs; no shell. |
| Public app → file connector | Только ответ на outbound connector connection | Device identity, allowlist paths, source ACL, audit. |
| Backend → Odoo | Отдельно согласованный API/service account | Минимальные scopes, ограничения операций, никакого production SQL. |
| Odoo → document check service | Только allowlisted TLS endpoint в production | Запрет произвольных URL/SSRF; аутентификация и ограничение payload. |

## 5. Открытые архитектурные решения

1. Есть ли утверждённый VPS/облако для public tier; иначе нужен минимальный обоснованный вариант.
2. Где происходит аутентификация: корпоративный IdP/SSO, Odoo или отдельный app identity store.
3. Где и на каких условиях хранятся originals, chunks, embeddings, chat history и audit.
4. Совместимы ли фактическая Odoo.sh edition/version и Git workflow с данным Docker-репозиторием.
5. Можно ли использовать внешних model providers; пока они выключены по умолчанию.

До ответов на эти вопросы эта схема — проектный ориентир, а не инструкция по deployment.
