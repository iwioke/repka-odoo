# Architecture: AI-проверка транспортных документов

**Статус:** Черновик MVP — часть инфраструктурных решений ожидает уточнения
**Продукт:** РЕПКА / Экспедирование
**Версия:** 0.1
**Дата:** 2026-09-21

## 1. Решения, подтверждённые на старте

| Вопрос | Решение |
| --- | --- |
| Где работает AI | Внутри инфраструктуры компании. |
| Связь CRM и AI | Отдельный AI-сервис, без прямого доступа к базе CRM. |
| Когда запускать проверку | Автоматически при загрузке документа. |
| Что AI делает в CRM | Возвращает рекомендации и черновые поля; логист подтверждает изменения. |
| Первичная задача | Проверка транспортных документов: тип, реквизиты, соответствие заказу, комплектность. |
| Документы первого сэмпла | CMR, заявка на перевозку, счёт и акт. |
| Обработчик первого сэмпла | Детерминированный mock: воспроизводимые результаты без подключения реальной модели. |
| Критичная ошибка CMR | Отсутствие подписи/печати получателя блокирует закрытие заказа до исправления или разрешения уполномоченного пользователя. |
| Размещение первого сэмпла | Отдельный Docker-контейнер на текущем внутреннем хосте Odoo, в изолированной сети и без доступа к PostgreSQL. |

## 2. Рекомендованная архитектура MVP

```text
Логист
  │ загружает документ
  ▼
REPKA / Odoo CRM
  │ 1. сохраняет исходный файл у себя
  │ 2. создаёт запись AI-проверки со статусом queued
  │ 3. отправляет задачу по внутреннему HTTPS API
  ▼
AI Document Check Service
  ├─ API приема заданий
  ├─ очередь фоновой обработки
  ├─ OCR и классификация документа
  ├─ извлечение структурированных полей
  ├─ модуль правил сопоставления
  ├─ журнал результатов
  └─ callback результата в CRM
  │
  ▼
REPKA / Odoo CRM
  ├─ отображает статус и замечания
  ├─ показывает черновики полей
  ├─ создаёт задачу ответственному при критичной ошибке
  └─ ожидает подтверждения логиста перед любым изменением
```

### Почему именно так

1. **Разделение ответственности.** CRM остаётся источником учётных данных и прав доступа; AI отвечает только за анализ.
2. **Нет прямого доступа к БД.** У AI-сервиса нет учётных данных PostgreSQL и он не читает filestore напрямую.
3. **Асинхронность.** Загрузка файла не ждёт OCR/AI и не блокирует работу логиста.
4. **Контролируемость.** Все решения AI возвращаются в структурированной форме, а не в виде свободного текста.
5. **Безопасность.** Передаётся минимальный контекст одного заказа и одного документа; связь и аутентификация ограничиваются внутренней сетью.
6. **Надёжность.** Повторная попытка, идемпотентность и журнал заданий позволяют не потерять результат при временной ошибке сервиса.

## 3. Взаимодействие сервисов

### 3.1. Создание задания

После появления нового документа CRM создаёт сущность `AI Document Check` и отправляет запрос в AI-сервис:

```json
{
  "request_id": "uuid",
  "document_id": "crm-document-id",
  "order": {
    "number": "EXP-DEMO-001",
    "carrier": "ООО «Демо Транс»",
    "shipper": "...",
    "consignee": "...",
    "route": ["Минск, Беларусь", "Варшава, Польша"],
    "cargo": {"description": "Бытовая техника", "weight_kg": 8500, "packages": 18},
    "vehicle": {"truck": "DEMO-1001", "trailer": "DEMO-2001"},
    "required_document_types": ["transport_request", "cmr", "invoice", "act"]
  },
  "document": {
    "filename": "cmr-demo.pdf",
    "media_type": "application/pdf",
    "content_url": "one-time internal URL"
  }
}
```

В демонстрационном образце вместо реального файла и идентификаторов используются только выдуманные значения.

### 3.2. Результат AI-сервиса

AI-сервис возвращает callback с идемпотентным `request_id`:

```json
{
  "request_id": "uuid",
  "status": "attention",
  "document_type": {"value": "cmr", "confidence": 0.98},
  "extracted_fields": [
    {"name": "document_number", "value": "CMR-DEMO-001", "confidence": 0.97},
    {"name": "weight_kg", "value": 9250, "confidence": 0.96}
  ],
  "checks": [
    {
      "code": "cargo_weight_mismatch",
      "severity": "warning",
      "document_value": 9250,
      "crm_value": 8500,
      "message": "Вес в CMR отличается от веса в заказе на 750 кг."
    },
    {
      "code": "consignee_stamp_missing",
      "severity": "critical",
      "message": "Не обнаружена отметка получателя в CMR."
    }
  ],
  "model": {"name": "deterministic-mock", "version": "0.1"}
}
```

CRM хранит этот ответ, показывает его логисту и применяет предложения только после явного подтверждения.

## 4. Компоненты

| Компонент | Ответственность | Данные |
| --- | --- | --- |
| Odoo addon `repka_ai_document_check` | Отслеживает загрузку, создаёт задания, передаёт минимальный контекст, принимает результат, показывает UI и аудит. | Идентификатор заказа, документ, результат, решение логиста. |
| Внутренний API AI-сервиса | Аутентифицирует CRM, принимает задания и отдаёт технический статус. | Временный контекст одного задания. |
| Очередь заданий | Изолирует фоновые и повторные обработки. | Идентификаторы и метаданные задач. |
| OCR / классификатор | Преобразует скан в текст, определяет тип документа. | Временная копия файла и извлечённый текст. |
| Извлекатель полей | Возвращает поля в строго определённой JSON-схеме. | Текст/изображение и схема. |
| Rule engine | Сравнивает значения документа и CRM, проверяет комплектность. | Извлечённые и ожидаемые значения. |
| Хранилище аудита | Фиксирует технический результат и подтверждение человека. | Время, версия модели, результат, пользовательское решение. |

## 5. Поток обработки и состояния

```text
queued → processing → completed
                    ↘ attention
                    ↘ blocked
                    ↘ failed
                    ↘ retrying → processing
```

- `queued`: CRM зарегистрировала задание.
- `processing`: AI-сервис принял файл и начал обработку.
- `completed`: существенных замечаний нет.
- `attention`: есть замечания или требуется подтверждение.
- `blocked`: критичная документальная ошибка блокирует закрытие заказа до исправления или разрешения уполномоченного пользователя.
- `failed`: техническая ошибка или файл не обработан.
- `retrying`: повтор после временной ошибки.

Каждый запрос должен быть идемпотентным: повторная доставка одного `request_id` не создаёт дубли задач, задач логисту и результатов.

## 6. Безопасность и защита данных

1. CRM и AI-сервис размещаются во внутренней сети; внешний доступ к AI API закрыт.
2. Взаимодействие использует HTTPS, отдельную сервисную учётную запись и ротацию секрета. Для production предпочтительны mTLS или OAuth2 client credentials; для демонстрации допускается отдельный секрет в защищённом хранилище.
3. AI получает только один файл и минимум данных конкретного заказа.
4. AI-сервис не получает подключение к PostgreSQL, пароль Odoo или доступ к файловому хранилищу CRM.
5. Временные файлы удаляются после настраиваемого срока; срок должен быть согласован до production.
6. Результат содержит только структурированные поля, уверенность, правила и ссылки на источник. Он не должен формировать непроверяемые юридические выводы.
7. Доступ к исходному файлу и результату наследует права на заказ в CRM.
8. В логах запрещены токены, содержимое документов, пароли и персональные данные сверх минимально нужного уровня.

## 7. Эксплуатация

- AI-сервис запускается отдельным контейнером или набором контейнеров, независимо от Odoo.
- Для MVP допустимо развернуть его на том же внутреннем сервере в отдельной сети Docker; для production рекомендуется отдельная VM или кластер, если нагрузка или требования безопасности этого потребуют.
- Задания должны иметь таймаут, контролируемые повторы и технический мониторинг.
- Необходимы метрики: очередь, длительность OCR/AI, доля ошибок, доля повторов, latency callback, процент подтверждённых полей.
- Изменение модели или набора правил версионируется: результат всегда хранит использованную версию.

## 8. Подтверждённые и открытые решения

### Подтверждено

- Первый сэмпл запускается отдельным контейнером рядом с Odoo на текущем внутреннем Docker-хосте. Контейнеры находятся в отдельной сети, а AI-сервис не имеет доступа к PostgreSQL.
- Для сэмпла допускается Docker Compose и детерминированный mock вместо реальных OCR/AI-моделей.
- В первой демонстрации проверяются заявка на перевозку, CMR, счёт и акт.
- CMR без подписи или печати получателя является критичной ошибкой и блокирует закрытие заказа.

### Инфраструктура

1. Какие ресурсы доступны для последующего подключения локальных OCR и нейросети: CPU, RAM, GPU, ограничения ОС?
2. Нужны ли резервное копирование результатов и отказоустойчивость уже в MVP?

### Данные и документы

3. На каких языках будут реальные документы: русский, белорусский, польский, английский, другие?
4. Какие поля CMR считаются обязательными именно для вашего процесса помимо подписи/печати получателя?
5. Как долго AI-сервис может временно хранить скан и извлечённый текст после проверки?

### Интеграция и процессы

6. Где в текущем интерфейсе логист загружает документы: только в заказ, только в подзаказ или в обоих местах?
7. Нужна ли повторная проверка после замены файла или изменения ключевых полей заказа?
8. Кого назначать ответственным за критическое замечание: автора заказа, операционного ответственного, другого сотрудника?
9. Какое время обработки одного документа приемлемо для логиста?

### AI и качество

10. Нужна ли обязательная визуальная привязка каждого извлечённого поля к фрагменту скана?
11. Какой минимальный уровень уверенности должен позволять показывать поле как черновик?
12. Кто будет размечать и подтверждать ошибки, чтобы измерять качество и улучшать правила/модель?
