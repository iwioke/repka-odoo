# Архитектура: демонстрационные сценарии в Odoo

## Подтверждённые факты
Проект использует Odoo 18 CE, PostgreSQL 16 и Docker Compose; `compose.dev.yaml` по умолчанию фильтрует единственную базу `repka`. Инструкция для тестов модулей использует `repka_test` как отдельную базу, но её существование, содержимое и установленный набор модулей сейчас не проверены. Четыре сценария из `ai_automations/scenarios/` работают на примерах JSON через `.internal/engine.py` и не записывают данные в Odoo. В `repka_ai_document_check` уже есть мастер, создающий синтетические записи документов и проверки, но механизма очистки сессии и интеграции всех четырёх сценариев нет. В текущем окружении `docker` установлен, но команда `docker compose` отсутствует, а `docker ps` не подключается к daemon Docker Desktop (`desktop-linux`); проверить базу и Odoo-тесты здесь пока невозможно.

## Согласованное с пользователем
Один демонстратор показывает свой экран заказчику; один показ одновременно; база — `repka_test` (пользователь предполагает, что она находится в Docker, но это не подтверждено); все четыре реализованных демо; только синтетические данные. Завершение кнопкой «Завершить показ» или штатным выходом из Odoo (Logout); удалять только принадлежащие сессии записи, не возвращать всю базу из резервной копии. Запуск на боевой базе и использование реальных клиентов не входит в задачу.

## Реализация в исходниках (не установлена и не проверена в Odoo)
Отдельный addon `repka_ai_demo_showcase`, который не входит в `repka_suite`, ограничен базой `repka_test` и группой `base.group_system`. Меню Odoo содержит демо-сессию с исходными синтетическими клиентами, заказами, документами и отдельными результатами. `compose.dev.yaml` монтирует `ai_automations/` в контейнер только для чтения; addon вызывает исключительно четыре фиксированных `run.py` без пользовательских путей и параметров. Записи создаются только новыми с меткой демо-сессии, с повторным использованием оригинальных JSON-примеров; результаты записываются как текст и машинный JSON по отдельным срезам. Никаких вычислений из `engine.py` не копируется. Кнопка «Завершить показ» подтверждается оператором; ORM удаляет только результаты, проверки, документы, экспедиционные и базовые заказы, партнёров этой сессии, затем саму сессию. Проверка не относящихся к демо проверок блокирует очистку; ошибка приводит к откату транзакции. Путь штатного `/web/session/logout` также вызывает очистку до выхода. Не вызывается `DROP DATABASE`, не восстанавливается общий снимок и нет фоновой очистки. Закрытие вкладки без Logout сохраняет показ до ручного завершения при следующем входе.

Данные в Odoo — снимки примеров при подготовке показа. Если демонстратор редактирует заказ отдельно, повторный запуск по-прежнему использует версионированный пример JSON, а не отредактированную строку базы. Интерфейс должен ясно показывать эту границу; подключение живого чтения Odoo не входит в MVP.

## Безопасность, эксплуатация и ошибки
Доступ только Odoo-администратору (`base.group_system`) базы `repka_test`; для просмотра синтетических записей addon добавляет этому кругу пользователей только права чтения нужных UFS-моделей. Создание/удаление связанных записей выполняется через `sudo()` только после проверки базы, владельца и состояния сессии. Реестр сценариев фиксирован, путь к входу пользователя не принимается, выход ограничен 1 МБ и время запуска 12 сек. Ошибка очистки не должна частично удалять записи: вызов ORM выполняется в транзакции Odoo. Другие пользователи тестовой базы могут видеть синтетические записи в общих списках, если их обычные права это позволяют: изоляции по record rules в текущем MVP нет. Не запускайте параллельные показы. Закрытие вкладки не очищает данные — при следующем входе оператор вручную завершает незакрытый показ. Заказчику отдельный аккаунт не нужен.

## Запуск и проверка после восстановления среды
На этой машине Docker daemon не запущен, `docker compose` отсутствует, поэтому установка addon и тесты Odoo пока не выполнялись. Сначала проверить существование `repka_test`, работоспособность Compose, её резервную копию и используемое значение `ODOO_DB_NAME`; не направлять Odoo случайно к `repka`. В `repka_test` установить только `repka_ai_demo_showcase` (он зависит от существующего `repka_ai_document_check`, но не включён в `repka_suite`). Затем выполнить тесты addon согласно `AGENTS.md` с `-d repka_test -i repka_ai_demo_showcase --test-enable --test-tags=/repka_ai_demo_showcase --stop-after-init`; после этого руками проверить в Odoo: начало показа → исходные записи → четыре результата → повторный запуск → кнопка завершения → отсутствие демо-записей; отдельно новый показ → штатный Logout → отсутствие записей после нового входа. Не запускать тесты/очистку на имеющей пользовательские данные базе без проверки её состояния и отдельного подтверждения.


## Открытые вопросы и допущения
- **Окружение:** пользователь предполагает, что Odoo работает в Docker, но daemon Docker Desktop не отвечает и Compose отсутствует. Существует ли `repka_test`, какие модули в ней установлены и как безопасно запустить её без влияния на `repka`?
- **Данные:** фактические ограничения, каскадное удаление, filestore и поведение сторонних расширений требуют проверки в `repka_test` перед показом.
- **Эксплуатация:** нужен ли в будущем TTL для забытых сессий? На текущем этапе согласовано вручную завершать их после следующего входа. Кто отвечает за восстановление после ошибки очистки?

Ответы о состоянии базы и тестирование ORM необходимы до установки addon и удаления даже синтетических записей в действующей `repka_test`. В этой работе изменений базы и её файлов не выполнялось.
