# PRD: Демонстрация AI-сценариев внутри Odoo

## Проблема и пользователи
Заказчик должен видеть в интерфейсе Odoo наглядный эффект автоматизаций на тестовой базе, а не отдельный локальный сайт с JSON. Демонстратор проводит один показ за раз на своём компьютере и показывает заказчику свой экран; вход заказчика в Odoo не требуется. Существующий каталог из 23 идей и четыре запускаемых CLI-сценария пока не подключены к Odoo.

## Цель и ценность
Показать четыре настоящих сценария (профиль клиента, экономика перевозок, готовность документов, сводка руководителю) на синтетических данных прямо в Odoo, позволяя увидеть исходные данные, результат и разницу до/после. После кнопки «Завершить показ» или штатного выхода из Odoo удалять только записи, созданные для этого показа, не затрагивая другие записи тестовой базы `repka_test`.

## Границы MVP и пользовательский путь
1. Демонстратор открывает `repka_test` и запускает демонстрационную сессию в Odoo.
2. Odoo создаёт/показывает исключительно синтетические данные, связанные с идентификатором этой сессии.
3. Демонстратор выбирает один из четырёх реализованных сценариев, видит исходные данные и полученный от существующего движка результат в интерфейсе Odoo; повторяет для остальных.
4. Демонстратор нажимает «Завершить показ» либо штатно выходит из Odoo; Odoo очищает только результаты и синтетические записи этой сессии. В исходных бизнес-записях изменений нет.
5. Если окно просто закрыто без Logout, браузер не гарантирует очистку; срок и способ удаления забытых сессий пока не согласованы.

## Функциональные и нефункциональные требования
- Отдельный раздел в Odoo на русском языке, доступный только демонстратору с утверждёнными правами.
- Чётко показывать «ДЕМО», «синтетические данные» и «детерминированные правила, не обученный ИИ/LLM». `LIVE` не включать.
- Запускать реальную логику четырёх сценариев из `ai_automations/`, без копирования вычислений и без доступа к боевым данным.
- Возможность видеть историю только в пределах демонстрационной сессии, а до/после — только в пределах созданных данных; не выдавать результаты за рабочие показатели организации.
- При повторном запуске не дублировать исходные синтетические записи (новый результат запуска допускается); ошибки показывать понятно, без секретов; не отправлять сообщения, не изменять платежи и не закрывать реальные заказы.
- Не применять откат всей `repka_test` или общий `DROP DATABASE`; сброс затрагивает только записи, принадлежащие демо-сессии. Вложения, если будут создаваться, тоже должны удаляться через Odoo ORM в рамках их демо-записей.

## Данные
Источники примеров — `ai_automations/scenarios/*/example_input.json`. Технические модели для будущих/демонстрационных экранов: `res.partner`, `ufs.base.order`, `ufs.forwarder.order`, `ufs.transport.document` и модель демо-результата (конкретная схема после проверки обязательных полей и зависимостей). Не копировать реальные записи и не сохранять персональные данные заказчика в демо.

## Метрики и приёмка
Заказчик видит результаты четырёх сценариев в Odoo, исходные/демо-данные и их изменение; результаты совпадают с CLI на том же примере; после «Завершить показ» не остаётся записей текущей демо-сессии; контрольные тестовые записи другого происхождения неизменны. Ошибка запуска не оставляет частично созданные данные. UI и права проверены на `repka_test`, не на базе `repka` или production. Число демонстраций и результаты не являются показателем бизнес-эффективности.

## Риски, ограничения и дальнейшие этапы
Потеря данных при удалении не тех записей, общий просмотр синтетических записей другими пользователями, остаточные вложения, фоновые задания, закрытие окна без кнопки, несовпадение данных JSON с обязательными полями Odoo. `repka_test` используется в проекте для тестов модулей, но фактический состав базы и режим доступа не проверены. Не устанавливать модуль/не очищать базу до согласования ограничений и возможности запустить Odoo локально. В будущем: TTL/автоочистка, отдельная демонстрационная база, проверенный live API и права заказчика — отдельные решения.
